## OpenCode Mobile productionization
- Built `opencode-mobile` app + bridge structure and moved toward productionization rather than MVP-only framing.
- Confirmed host initially lacked `opencode`; installed `opencode-ai` globally and verified `opencode` v1.2.24 is available.
- Verified real OpenCode JSON runtime path with `opencode run --format json` and adapted the bridge parser to handle OpenCode JSON events (`text`, `tool_use`, `step_finish`) and strip `<think>` blocks.
- Verified real E2E bridge flow against OpenCode: session create, message send, `tool_use` capture, assistant response streaming, and runtime session ID capture all work.
- Verified OpenCode session continuity with `--session`, `--continue`, and `--attach`; updated bridge to reuse `runtimeSessionID` when available so repeated messages can stay on the same OpenCode session.
- Verified approval-style behavior in real runtime is expressed as assistant text asking whether to continue, not as a native structured approval event; captured raw transcript showing: "Would you like me to run any further commands? Please let me know what you'd like to do next."
- Added bridge-side approval detection based on approval-question phrasing in assistant text and fixed a false-positive bug so ordinary outputs like `APPROVED_BY_USER` no longer create `approval.requested`.
- Verified `approval.requested` now appears end-to-end for a real OpenCode approval-style prompt, and `approval.respond` currently acts as bridge-side next-command consent that influences the next message context.
- Verified cancel behavior currently works at the bridge semantic level (`task.cancel` -> `task.error: Task cancelled` + session back to idle), but native OpenCode process interruption is still not proven.
- Updated app to surface real runtime metadata from bridge events: `runtimeSessionID`, `lastTool`, runtime activity, host/runtime info, and consent state.
- Current main remaining production gaps: native cancel semantics, QR scanner implementation, and general restart/operational hardening.
- User accepted the Android emulator-based happy path as verified enough to repurpose the autotest lane for ongoing production hardening and regression testing, but explicitly raised the completion bar: do not declare done on happy-path success alone; only declare completion when P0/P1 release blockers are resolved.
- Added a formal emulator regression plan in `opencode-mobile/EMULATOR_REGRESSION_MATRIX.md` covering: reconnect, bridge restart during active session, timeout/unreachable bridge, invalid QR payload, empty/error/retry UX, and approval/cancel flow, each with pass/fail criteria and required evidence sources.
- Kept `EXPO_PUBLIC_AUTOTEST_*` explicitly test-only and separate from the production runtime path; this autotest lane is now intended as the official regression tool rather than part of normal app behavior.
- Identified a release blocker around weak disconnect/unreachable UX and fixed it by adding bridge connect timeout handling, a synthetic `connection.closed` event on socket close, disconnected-state UI handling, and a visible retry action; added regression tests for timeout and socket-close behavior.
- Important caution from this cycle: Android emulator/JDK/adb toolchain evidence was inconsistent, so emulator-related completion claims should only be made when backed by direct logs/screenshots/persisted state, not inferred from partial setup.
